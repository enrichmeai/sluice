# evals

The frozen eval set and the report that gates every model.

## The freeze rule

The set under `cases/` is frozen from the merge that added each case. A case is never edited
after that: a wrong or outdated case is **retired** (moved to `cases/retired/`, kept for the
record) and a corrected one gets a **new id**. Every report names the ids it ran, so a number
from last month means the same thing today. No case text ever enters a training set:
`check_cases.py` hashes each request and refuses any that appears in
`training/data/requests.sha256` once that file exists.

## Layout

```
cases/<task>/<task>-NNN.yaml   one case each; ids are unique and match the file name
schemas/*.json                 BigQuery schema exports: tables, columns, types. Never rows.
inputs/<name>/                 files a case hands the model besides the schema (e.g. Culvert's macros)
fixtures/red/                  cases broken on purpose; check_cases.py must fail on them
check_cases.py                 the gate (python3 -I evals/check_cases.py)
test.sh                        red on fixtures/red, then green on cases/
report.md                      regenerated by the runner (step 3); absent until then
```

## A case

```yaml
id: dbt-bq-005            # <task>-NNN
task: dbt-bq
tags: [incremental, join, culvert]
request: >-               # the plain-language ask, as a user would write it
  Build the FDP model event_transaction_excess ...
input:
  schema: schemas/culvert_odp_generic.json   # relative to evals/
  project: inputs/culvert_macros             # optional: files already in the project
expect:
  sources: [{name: odp_generic, tables: [customers, accounts]}]
  models:
    - name: event_transaction_excess
      path: models/fdp/event_transaction_excess.sql   # optional
      materialized: incremental
      unique_key: event_key
      incremental_strategy: merge                     # required when incremental (the Culvert way)
      refs: [stg_generic_customers, stg_generic_accounts]
      sources: [odp_generic.customers]                # tables it may read
      partition_by: _extract_date
      cluster_by: [customer_id, account_id]
      derived: [event_key, customer_status]           # output columns that are not schema columns
      columns_required: [event_key, customer_id, ...] # must appear in the model's output
      columns_forbidden: [ssn]                        # must not (PII cases)
      macros_used: [mask_partial_last4]
      tests: {event_key: [not_null, unique]}
      unit_tests_min: 1
  columns_from_schema_only: true
  missing_inputs: [customers.email]   # for cases whose right answer names a gap
  expected_response: ...              # what a correct answer says, for the judge
validators: [dbt_lint, dbt_parse]     # which validators/ scripts must pass
```

`check_cases.py` checks the shape: ids, schema files, that every table and column an assertion
names exists in the schema (or is declared `derived`), that every `missing_inputs` entry really
is missing, that incremental models name a `unique_key` and `merge`, and the count per task. The
runner (step 3) checks the model's output against `expect`.

## dbt-bq: 24 cases (frozen 2026-11-08)

| Cases | What they cover |
|---|---|
| 001–004 | staging views over Culvert's four generic ODP tables |
| 005–008 | incremental merge marts: a join, two maps, and the three-way CDP join |
| 009–010 | PII masking with Culvert's `pii_masking.sql` macros, handed in via `inputs/culvert_macros` |
| 011–015 | jaffle_shop: staging, the customers and orders marts, a daily aggregate, an incremental fact |
| 016–018 | tests as the point: relationships and accepted_values; unit tests per branch; partition and cluster config |
| 019–022 | missing inputs: the correct answer names what the schema lacks instead of inventing it |
| 023–024 | sources.yml with freshness and source tests; a reconciliation row-count model |

Every request that needs a surrogate key says "no dbt packages", because the offline
`dbt_parse` validator installs none (a model must not depend on packages the job container does
not install).

## Metrics (written by the runner in step 3)

Per model and tier: first-try pass rate, pass rate after ≤3 repairs, mean repairs, tokens out,
wall time, peak RAM at q4_k_m. Release gate (`docs/BUILD_PROMPT.md` § 6): a fine-tune ships only
if it beats the untuned base on first-try offline pass rate here and loses no more than 5 points
on the generic code set.
